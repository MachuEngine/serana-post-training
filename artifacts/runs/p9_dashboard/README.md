# Grafana 대시보드 — 렌더링된 패널

`deploy/grafana/serana-dashboard.json`의 패널 8개를, 실제 트래픽이 흐르는
동안 Grafana의 렌더링 API로 뽑은 PNG다.

**왜 파일로 남기나.** 대시보드는 클러스터가 떠 있는 동안에만 존재하고,
이 프로젝트는 비용 때문에 클러스터를 세션마다 만들고 지운다. "모니터링이
어땠는지 보려면 클러스터를 다시 띄우세요"는 읽는 사람에게 너무 큰 요구다.
`scripts/render_dashboard.py`가 패널 목록을 대시보드 JSON에서 읽어오므로,
패널을 추가하면 캡처도 따라온다.

## 이 그림들이 찍힌 조건

| | |
|---|---|
| 부하 | 120건, 동시성 4, config 3종(sft/dpo/b) 순환, `max_tokens 64` |
| 스크립트 | `scripts/gateway_load.py` |
| 결과 | 120건 전부 HTTP 200, 오류 0건 |
| 시간 창 | 최근 8분 |

## 읽을 때 주의

**이 지연 수치는 성능 측정값이 아니다.** 게이트웨이 p50 4.06초, p95 7.61초로
나오는데, P5가 격리된 조건에서 측정한 p95 0.42~0.84초와 비교하면 안 된다.
차이의 이유는 둘이다 — 세 config를 섞어 돌렸고, B 설정은 SFT보다 약 6배 긴
답을 만든다. 측정은 `scripts/throughput_sweep.py`가 하고, 하드웨어 표의
숫자는 거기서 나온다. 이 그림들의 목적은 **패널이 실제 데이터에 연결돼
있음을 보이는 것**이다.

## 패널

| 파일 | 내용 |
|---|---|
| `02-request-rate-by-config` | config별 요청률. 결과표와 같은 축으로 나눈다 |
| `03-error-ratio-5m` | 5분 오류율. 경보 임계값 5% |
| `04-gateway-latency-p50-p95-p99` | 호출자가 체감하는 전체 지연 |
| `06-running-vs-waiting-requests` | 실행 중 3~4건, 대기 0~1건 — 동시성 4와 일치 |
| `07-kv-cache-utilization` | §7.4가 예측하고 검증한 KV 캐시 예산의 실시간 값 |
| `08-token-throughput` | 생성/프롬프트 토큰 처리량 |
| `09-time-to-first-token` | vLLM이 직접 재는 TTFT. 게이트웨이에서 재구현하지 않았다 |
| `10-queue-time-and-preemptions` | 큐 대기가 늘면서 KV 캐시가 높으면 포화, 아니면 단순히 느린 것 |

## 오류율 패널에 대하여

처음 버전은 오류가 0건일 때 "0%"가 아니라 **"데이터 없음"**을 표시했다.
오류 시계열 자체가 존재하지 않으면 나눗셈 전체가 비기 때문이다. `or vector(0)`을
넣어 고쳤고, 같은 문제가 경보 규칙에도 있었다(식이 비면 경보가 영원히 발동하지
않는다). 살아 있는 Prometheus에서 수정 전후를 비교해 확인했다 —
`03-error-ratio-5m.png`가 0%를 표시하는 것이 그 결과다.
