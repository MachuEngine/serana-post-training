# 2x L4 DDP 확장성 측정 — 결과

**측정일 2026-09-12. GCP가 아니라 RunPod(2x NVIDIA L4, on-demand)에서 실행.**
`p7_ddp_plan.md`는 GCP 할당량 거절로 BLOCKED 상태였고, 이 문서가 그 후속이다.
원시 로그: `artifacts/runs/ddp_logs/`.

## 결과

| | 1-GPU | 2-GPU (DDP) |
|---|---|---|
| 스텝 시간 | **22.90 s/step** | **11.75 s/step** |
| 완주 스텝 | 25 / 150 (중단, 아래 한계 참조) | 150 / 150 |
| GPU당 최대 VRAM | — | ~20.8 GB (nvidia-smi) |
| GPU 전력 | — | 67~69 W / 72 W |

- **속도 향상 1.95x** (이상적 2.00x)
- **병렬 효율 97.4%**

2-GPU 벽시계 시간은 150스텝에 2358.7초였다. 스텝당 14.98초인데, 이 값에는
25스텝마다 도는 검증과 모델 로딩이 섞여 있어 GPU 개수에 비례해 줄지 않는다.
확장 효율은 순수 학습 스텝 시간(11.75s)으로 계산했다.

### 예측 대비

| 항목 | 예측 | 실측 | 오차 |
|---|---|---|---|
| 1-GPU 스텝 | ~20 s | 22.90 s | +14% |
| 2-GPU 스텝 | ~11 s | 11.75 s | +7% |
| 속도 향상 | 1.8x | 1.95x | +8% |
| 병렬 효율 | 90% | 97.4% | +8% |

모두 20% 이내. 효율이 예측보다 높게 나온 이유는 아래 참조.

## 왜 1.95x인가 — 통신량이 작기 때문

DDP가 매 스텝 주고받는 것은 **학습 대상 파라미터의 기울기뿐**이다. LoRA는
r=16을 q/k/v/o 투영에만 걸어 8.2B 중 약 **18.9M(0.23%)** 만 학습하므로,
스텝당 all-reduce 페이로드는 bf16 기준 **약 38MB**에 불과하다. 계산이
11.75초 걸리는 동안 38MB를 옮기는 것은 병목이 되지 않는다.

즉 이 97.4%는 DDP가 빠르다는 증거가 아니라 **LoRA가 통신을 거의 없앤다**는
증거다. 같은 실험을 전체 미세조정으로 했다면 스텝당 약 16GB를 주고받아야
하므로 효율은 크게 떨어졌을 것이다. 이 수치를 인용할 때는 어댑터 학습이라는
전제를 함께 밝혀야 한다.

## 환경 제약 — P2P를 꺼야 돌았다

`NCCL_P2P_DISABLE=1` 없이는 **첫 all-reduce에서 무한 대기**했다. 증상:

- NCCL 초기화는 성공하고 `Channel 00~03 ... via P2P/CUMEM`까지 확보된다
- 그 직후 양쪽 랭크가 GPU 사용률 100%, **전력 31~35W / 72W**, 온도 34도로 고정
  (실제 학습 시 67~69W, 70도) — 계산 없이 대기만 반복하는 상태
- 10~30분 뒤 NCCL 워치독 타임아웃으로 프로세스 종료

즉 **P2P 연결 협상은 성공하지만 실제 전송이 되지 않는** 환경이었다. 가상화된
클라우드 GPU에서 PCIe 설정 때문에 생기는 알려진 문제다. P2P를 끄면 기울기가
호스트 메모리를 거쳐 오가는데, 위의 이유(페이로드 38MB)로 그래도 효율이
97.4% 나왔다.

배제 과정에서 다음은 원인이 아님을 확인했다:

| 의심한 것 | 배제 근거 |
|---|---|
| 4-bit 양자화 (bitsandbytes) | bf16으로 바꿔도 동일하게 대기 |
| 기울기 체크포인팅 재진입 | `use_reentrant=False`, 체크포인팅 완전 해제 모두 동일 |
| `ddp_find_unused_parameters` | 값을 바꿔도 동일 |
| `/dev/shm` 부족 | 88GB로 충분 |
| 호스트 RAM 부족 | 503GB 중 463GB 여유 |

최소 재현은 `scripts/profile_ddp.py`(Trainer·데이터셋 없이 모델+LoRA+DDP로
forward/backward 6회)로도 동일하게 재현됐다.

## 한계 — 동일성 검증 미완

계획서(`p7_ddp_plan.md`)의 성공 기준 2번, **"전체 배치를 16으로 고정했을 때
1-GPU와 2-GPU의 손실 곡선이 겹치는가"** 는 확인하지 못했다.

두 실행의 손실 기록에 **겹치는 스텝이 없다**:

- 1-GPU: 스텝 5~25 (웹 터미널 연결이 끊기며 25스텝에서 중단)
- 2-GPU: 스텝 30~150 (초반 기록이 터미널 로그에 남지 않음)

```
스텝:    5      10     15     20     25  │  30     35     40
1-GPU:  2.516  1.890  1.362  0.772  0.299│
2-GPU:                                   │ 0.159  0.129  0.112
```

이어 붙이면 하나의 매끄러운 감소 곡선이 되어 전체 배치 고정이 작동했다는
정황은 되지만, 같은 스텝에서 두 값을 직접 대조한 것은 아니다. **"같은 학습을
더 빨리 돌린 것"임은 이 측정으로 증명되지 않았다.**

원인은 측정 설계의 두 가지 미비였다:

1. `ddp_bench.sh`가 각 실행의 `run_report.json`(`log_history` 포함)을
   회수하지 않고 터미널 로그에만 의존했다. 터미널 로그에는 tqdm 진행
   표시줄이 캐리지 리턴으로 섞여 들어와 기록이 덮어써진다.
2. 최종 실행을 tmux 밖에서 돌려, 연결이 끊기자 1-GPU가 25스텝에서 죽었다.

1번은 커밋 826118d에서 수정했다(두 실행의 `run_report.json`을 `results/`로
복사). 다시 측정하면 손실 곡선 비교까지 확보된다. 팟은 이미 삭제되어 이번
실행의 리포트는 복구 불가.

## 재현 방법

```bash
# 팟: 2x L4, on-demand, CUDA 12.9+, 컨테이너 60GB / 볼륨 50GB
# HuggingFace가 RunPod IP에 429를 걸므로 가중치는 ModelScope에서 받는다
uv pip install modelscope
python -c "from modelscope import snapshot_download; snapshot_download('Qwen/Qwen3-8B', local_dir='/workspace/qwen3-8b')"
uv pip install "bitsandbytes>=0.46.1"   # pyproject에 의도적으로 없음

tmux new -s ddp
NCCL_P2P_DISABLE=1 bash scripts/ddp_bench.sh 150 /workspace/qwen3-8b
```

## 비용

측정 자체는 2-GPU 39분 + 1-GPU 중단분. 환경 문제(드라이버 CUDA 버전 불일치,
디스크 부족, HuggingFace 429, P2P 대기) 진단에 쓴 시간을 포함해 RunPod에서
누적 **약 $9**.
